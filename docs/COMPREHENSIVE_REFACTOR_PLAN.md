# AuroraList 全面优化与重构计划

> **目标**: 从用户实际刊登流程出发，重新设计 UI 布局与功能架构，实现真正的"零人工干预、全自动化"批量处理

**创建时间**: 2026-11-24  
**当前版本**: v1.0.9  
**优化负责人**: Claude Opus 5

---

## 📋 执行原则

1. **用户流程优先**: 按照"连接 → 设置规则 → 选择商品 → 自动处理 → 查看结果"的自然顺序重组 UI
2. **平台统一**: 所有平台共享相同的功能结构和交互逻辑
3. **减少点击**: 一个任务不应该需要在多个页面间跳转
4. **配置一次**: 规则设置后应该能持久应用到所有后续批量任务
5. **渐进验证**: 每完成一个任务立即构建测试，确保无回归

---

## 🎯 核心问题诊断

### 当前架构问题

#### 1. **UI 布局混乱**
- ❌ "开始任务"卡片放在概览页，但商品选择在其他页面
- ❌ 同一功能分散在多个页面（如 AI 文案设置在独立页面，但运行在另一页面）
- ❌ 平台间布局不一致（Alibaba 有 7 个页面，TikTok 有 11 个页面）
- ❌ 内部路由页面（以 `__internal__` 分组）与用户导航页面混在一起

#### 2. **功能流程割裂**
- ❌ 用户需要在"连接店铺"→"AI设置"→"类目设置"→"概览"间反复跳转才能开始一次任务
- ❌ "搜索全部商品"按钮实际无作用但占据显眼位置
- ❌ 关键词采集和商品选择的入口不直观
- ❌ 批量处理结果没有统一的查看/重试入口

#### 3. **代码质量问题**
- ⚠️ `app.py` 文件过大（3000+ 行），违反单一职责原则
- ⚠️ 已删除的 `queue.py` 和 `scheduler.py` 但逻辑可能分散到其他地方
- ⚠️ 并发控制不清晰（`threading.Thread` 大量使用但无统一管理）
- ⚠️ 配置项过多（136+ 项）但无分层验证
- ⚠️ 事件总线（`progress.py`）与 UI 更新的线程安全性存疑

#### 4. **性能瓶颈**
- 🐌 图片处理串行化（虽有 `image_concurrency=4` 但实际控制粒度不细）
- 🐌 大量同步文件 I/O（`config.json` 每次修改都全量写入）
- 🐌 UI 更新频繁触发 `_safe_update()`，可能导致界面卡顿
- 🐌 日志面板未做虚拟滚动，超过 1000 条后会变慢

## 🏗️ 重构任务清单

### Phase 1: 代码审查与架构清理（P0 - 必须完成）

#### Task 1.1: 代码质量审查
- [ ] **并发安全审查**
  - 检查所有 `threading.Thread` 使用点
  - 确认 `_safe_update()` 的线程安全性
  - 审查 `progress.BUS` 事件总线的锁机制
  - 检查配置文件读写的竞态条件
  
- [ ] **内存泄漏检查**
  - 检查 Flet 控件是否正确释放
  - 审查图片处理后的 Pillow 对象清理
  - 检查定时器/线程是否正确关闭
  
- [ ] **错误处理规范**
  - 统一异常捕获策略（避免空 `except: pass`）
  - 添加关键路径的日志记录
  - 确保所有 API 调用有超时设置

#### Task 1.2: 代码重构
- [ ] **拆分 `app.py`**
  - 提取页面构建逻辑到独立模块（`ui/pages/`）
  - 提取公共 UI 组件到 `ui/components.py`
  - 状态管理独立到 `ui/state.py`
  - 目标：单文件不超过 500 行
  
- [ ] **配置系统优化**
  - 实现配置分层验证（`config.validate()`）
  - 添加配置迁移机制（版本升级时自动修复）
  - 配置文件改用增量写入（只写变更项）
  
- [ ] **并发控制统一**
  - 创建 `ThreadPoolManager` 统一管理线程
  - 实现任务队列系统（替代已删除的 `queue.py`）
  - 添加并发限制器（避免同时运行多个批量任务）

#### Task 1.3: 性能优化
- [ ] **图片处理优化**
  - 实现真正的并行处理（使用 `concurrent.futures`）
  - 添加图片尺寸预检（避免加载超大图片）
  - 实现渐进式图片上传（不等所有图片处理完再开始上传）
  
- [ ] **UI 渲染优化**
  - 日志面板实现虚拟滚动（只渲染可见区域）
  - 商品列表实现分页加载
  - 减少不必要的 `update()` 调用（批量更新）
  
- [ ] **配置持久化优化**
  - 配置修改改用防抖动（500ms 内多次修改只写一次）
  - 使用 SQLite 替代 JSON（更快的读写性能）

## 🚧 风险与缓解

### 风险 1: UI 重构导致功能回归
**缓解措施**:
- 每个页面重构前先写集成测试
- 保留旧代码作为参考（`app_legacy.py`）
- 渐进式迁移（先迁移一个平台，验证后再推广）

### 风险 2: 配置系统改动影响现有用户
**缓解措施**:
- 实现配置迁移脚本（自动转换旧配置）
- 保留旧配置备份（`config.json.bak`）
- 启动时自动验证配置完整性

### 风险 3: 性能优化引入新 Bug
**缓解措施**:
- 性能优化使用 Feature Flag 控制（可快速回滚）
- 压力测试（1000 商品批量处理）
- 内存泄漏检测（长时间运行测试）
